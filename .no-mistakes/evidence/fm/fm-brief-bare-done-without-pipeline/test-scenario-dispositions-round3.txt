## Scenario 1 - the completion signal is the pipeline PR, never a commit: DRIVABLE, driven

Disposition (a). Artifacts: dod-block-no-mistakes.txt (bin/fm-brief.sh --mode no-mistakes)
and fm-promote-delivered-dod-round3.txt (bin/fm-promote.sh --mode no-mistakes). Verbatim:

    **Completion for mode=no-mistakes is a PR the no-mistakes pipeline pushed and opened, never a commit.**
    A commit, a clean branch, or "ready for the run" is NOT completion; stopping there leaves the task unfinished and firstmate has to chase it.
    The one completion claim is `done: PR {url} checks green`, written with the PR's full `https://` URL once the run reports CI green.

## Scenario 2 - the worker starts the pipeline in a harness-agnostic form: DRIVABLE, driven

Disposition (a). dod-block-no-mistakes.txt contains 0 hard-coded `/no-mistakes`
invocations and defers the form to harness-adapters ("start this task's no-mistakes
pipeline yourself in your own harness's skill-invocation form"; "when you are unsure
of it, state the action in natural language and proceed").

## Scenario 3 - the fleet's own reader honors the pinned claim and rejects a commit-only claim: DRIVABLE, driven

Disposition (a). Artifact: fm-crew-state-claim-classification.txt. Real
bin/fm-crew-state.sh over a status log whose last line is the brief's claim, with a
monitoring run present:

    pinned claim      -> state: done  · source: status-log  (the fleet reclassifies it to done)
    commit-only       -> state: working · source: run-step · validating (running)
    PR not green yet  -> state: working · source: run-step · validating (running)
    pinned + head/CI  -> state: done  · source: status-log  (extra detail appended does not break the signal)

## Scenario 4 - the other delivery modes do not inherit the pipeline claim: DRIVABLE, driven

Disposition (a). Artifacts: dod-block-direct-PR.txt and dod-block-local-only.txt, each
generated by the real bin/fm-brief.sh. direct-PR keeps `done: PR {url}` and "Do NOT
start the no-mistakes pipeline"; local-only keeps `done: ready in branch <branch>`;
neither carries the no-mistakes completion block.

## Scenario 5 - the completion line must be the last status line: DRIVABLE, driven

Disposition (a). Artifact: fm-crew-state-completion-line-order.txt. Real
bin/fm-crew-state.sh reads the status log's LAST non-blank line, so:

    claim last                   -> state: done
    claim, then explanation      -> state: working (claim silently lost)
    explanation, then claim      -> state: done

The DoD's "The completion line is the LAST line in the status log" rule states real
reader behavior, not an aspiration.

## Residual A - a real worker on its own harness actually starting the run: NOT DRIVABLE IN-REPO

Disposition (b). Turning the delivered brief into an agent action needs a live crew
worker on a real harness driving a real repo and forge: the exact tools that are not
available to this step. `command -v codex` finds no codex CLI on this host (the
harness whose `/`<skill>` form the change exists to avoid), and no crew worker is
spawned here. Substituting evidence: the generated brief and the promoted worker's
ship instructions (Scenarios 1-2) are the whole delivered surface this change owns,
and tests/fm-brief.test.sh + tests/fm-task-delivery.test.sh pin that delivery
deterministically. Risk left unverified: whether a given model obeys the brief is
model behavior, evaluated in development, not a runtime the repo can assert.

## Residual B - a second validation start on a branch that already has an active run: NOT DRIVABLE IN-REPO

Disposition (b). The DoD tells the worker never to start a second run, to treat a
mid-run firstmate delivery as a nudge, and to follow the pipeline's own status on an
already-active-run refusal. Every one of those is the no-mistakes daemon's behavior
with a live run, and this step's phase boundary forbids invoking `no-mistakes init` /
`axi run` (never initialize or control another pipeline). Substituting evidence: the
generated brief pins the rule verbatim (Scenarios 1-2), and the supervisor contract
states the same ownership in AGENTS.md section 7 ("### Validate"). Risk left
unverified: the refusal wording matches whatever the installed no-mistakes binary
actually emits; the brief therefore routes the worker to the pipeline's own status
and help lines rather than to a refusal string this repo would have to guess, which
is the narrowing already applied in the previous round.
